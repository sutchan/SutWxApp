## 2. 项目背景与定位

### 2.1 项目背景

苏铁微信小程序（SutWxApp）是一款面向普通消费者的电商微信小程序，专注于提供精品植物和园艺用品。项目以"自然、品质、便捷"为核心理念，通过微信小程序的轻量级形态，为用户提供优质的购物体验。

### 2.2 项目定位

- **目标用户**：热爱植物、追求品质生活的消费者
- **核心价值**：优质商品、便捷购物体验、创新的积分系统
- **市场定位**：中高端植物园艺电商平台
- **产品形态**：微信小程序（轻量级、无需下载、即开即用）

### 2.3 项目目标

#### 短期目标（v3.0.0）
- 完成核心电商功能（商品浏览、购物车、订单管理）
- 实现用户中心和地址管理
- 建立完整的设计系统和组件库
- 确保基础安全防护

#### 中期目标
- 完善积分系统和社交功能
- 优化性能和用户体验
- 增加营销活动功能
- 提升安全防护等级

#### 长期目标
- 打造完整的植物园艺生态
- 建立用户社区
- 扩展更多品类和服务
- 实现数据驱动的运营

## 4. 设计系统

### 4.1 设计理念

项目采用 **Apple 极简设计风格**，结合 **shadcn/ui 设计理念**，核心特点：

- **极简主义**：减少视觉干扰，突出核心内容
- **清晰优先**：文字清晰易懂，层次分明
- **充足留白**：使用合理的间距创造清爽感
- **微妙动效**：平滑自然的过渡动画
- **深度层次**：通过阴影、圆角创造层次感

完整设计规范请参考 `design/spec.md`。

### 4.2 设计令牌

设计系统通过 CSS 变量（自定义属性）实现统一管理：

| 类别 | 示例变量 |
|------|---------|
| 颜色 | `--primary-color`, `--text-primary`, `--background-primary` |
| 间距 | `--spacing-xs`, `--spacing-md`, `--spacing-xl` |
| 字体 | `--font-size-h1`, `--font-size-md`, `--font-size-sm` |
| 圆角 | `--border-radius-sm`, `--border-radius-lg`, `--border-radius-xl` |
| 阴影 | `--shadow-sm`, `--shadow-md`, `--shadow-lg` |
| 动效 | `--duration-fast`, `--duration-normal`, `--ease-in-out` |

### 4.3 组件库

项目拥有 9 个自定义组件，分为三类：

| 类别 | 组件列表 | 数量 |
|------|---------|------|
| 基础组件 | Button, Badge, Avatar, Tag, Divider | 5 |
| 复合组件 | EmptyState | 1 |
| 业务组件 | ProductCard, Price, OrderCard | 3 |

组件开发规范请参考 `development/spec.md`。

## 6. 开发流程

### 6.1 开发工作流

```
需求确认 → 设计评审 → 技术方案 → 开发实现 → 代码审查 → 测试验证 → 发布上线
```

### 6.2 各阶段详细说明

#### 6.2.1 需求确认阶段
- 产品经理输出需求文档
- 开发和测试参与需求评审
- 明确需求范围、优先级和验收标准
- 输出：需求文档、用户故事、验收标准

#### 6.2.2 设计评审阶段
- 设计师输出设计稿和原型
- 产品、开发、测试参与设计评审
- 确认设计符合需求和设计规范
- 输出：设计稿、原型、评审记录

#### 6.2.3 技术方案阶段
- 开发负责人输出技术方案
- 评估技术复杂度和工作量
- 确定技术选型和实现方案
- 输出：技术方案文档、开发排期

#### 6.2.4 开发实现阶段
- 开发人员按照规范编写代码
- 遵循代码规范和组件规范
- 编写单元测试
- 本地自测通过
- 输出：功能代码、单元测试

#### 6.2.5 代码审查阶段
- 提交 Merge Request / Pull Request
- 至少一人审查通过
- 审查重点：代码质量、安全性、规范性
- 输出：审查意见、修改后的代码

#### 6.2.6 测试验证阶段
- 测试人员编写测试用例
- 执行功能测试、集成测试
- Bug 跟踪和修复验证
- 输出：测试报告、Bug 记录

#### 6.2.7 发布上线阶段
- 版本号更新
- 发布说明编写
- 小程序上传和审核
- 发布后监控
- 输出：发布版本、发布说明

### 6.3 Git 工作流

#### 6.3.1 分支策略

| 分支 | 说明 | 命名规范 |
|------|------|---------|
| main | 生产分支，保持稳定 | `main` |
| develop | 集成分支，用于测试 | `develop` |
| feature/* | 功能开发分支 | `feature/功能名称` |
| bugfix/* | Bug 修复分支 | `bugfix/bug编号-简述` |
| hotfix/* | 紧急修复分支 | `hotfix/版本号-简述` |
| release/* | 发布分支 | `release/版本号` |

#### 6.3.2 提交规范

使用语义化提交消息，格式：`<type>: <description>`

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复 bug |
| docs | 文档更新 |
| style | 代码样式修改（不影响功能） |
| refactor | 代码重构 |
| perf | 性能优化 |
| test | 测试相关 |
| chore | 构建或辅助工具变动 |
| security | 安全相关修复 |

**示例**：
```
feat: 添加收货地址管理功能
fix: 修复购物车数量计算错误
docs: 更新功能规范文档
security: 修复加密算法安全漏洞
```

#### 6.3.3 分支合并流程

```
feature → develop → release → main
              ↑
          bugfix/
          hotfix/
```

### 6.4 代码审查清单

代码审查时应检查以下内容：

- [ ] 代码符合编码规范
- [ ] 命名清晰、有意义
- [ ] 函数职责单一，不过长
- [ ] 关键逻辑有注释说明
- [ ] 没有硬编码的魔法数字
- [ ] 错误处理完善
- [ ] 敏感数据处理正确
- [ ] 没有性能问题
- [ ] 单元测试覆盖关键路径
- [ ] 文档同步更新

## 8. 文档规范

### 8.1 OpenSpec 文档体系

项目采用 OpenSpec 规范文档体系，包含以下文档：

| 文档 | 路径 | 说明 | 版本 |
|------|------|------|------|
| 项目规范 | `openspec/specs/project/spec.md` | 项目整体介绍、架构、流程 | 3.0.0 |
| 功能规范 | `openspec/specs/features/spec.md` | 功能需求、交互设计 | 3.0.0 |
| 设计规范 | `openspec/specs/design/spec.md` | 设计系统、组件规范 | 3.0.0 |
| 开发规范 | `openspec/specs/development/spec.md` | 代码规范、安全规范 | 3.0.0 |
| 测试规范 | `openspec/specs/testing/spec.md` | 测试策略、测试用例 | 3.0.0 |
| 原型设计 | `openspec/prototype/prototype.html` | 可交互原型 | 3.0.0 |

### 8.2 文档编写规范

#### 8.2.1 文件头规范

每个文档头部必须包含以下信息：

```markdown
<!--
文件名: spec.md
版本号: 3.0.0
更新日期: 2026-07-06
作者: Sut
描述: 文档功能描述
-->
```

#### 8.2.2 格式规范

- 使用 Markdown 格式编写
- 标题层级清晰（H1 → H2 → H3）
- 使用表格展示结构化数据
- 代码块使用正确的语法高亮
- 列表使用有序或无序列表
- 图片使用相对路径或 URL

#### 8.2.3 语言规范

- 文档使用中文编写
- 技术术语可使用英文
- 表述清晰、准确、简洁
- 避免歧义性描述

### 8.3 文档更新流程

1. **代码变更时**：同步更新相关文档
2. **版本发布时**：统一更新所有文档版本号
3. **定期审查**：每季度审查文档的准确性
4. **变更记录**：在版本历史中记录变更内容

## 9. 质量保证

### 9.1 质量目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 核心功能测试覆盖率 | 100% | P0 优先级功能 |
| 单元测试覆盖率 | ≥ 80% | 工具函数、服务层 |
| 页面加载时间 | ≤ 2s | 首屏加载 |
| 崩溃率 | ≤ 0.1% | 线上版本 |
| 安全漏洞 | 0 严重/高危 | 安全审计 |

### 9.2 测试策略

完整测试策略请参考 `testing/spec.md`。

**测试金字塔**：
- 单元测试（约 70%）：工具函数、服务层、组件
- 集成测试（约 20%）：页面与服务、组件协作
- UI 测试（约 10%）：核心业务流程

### 9.3 代码质量

- 遵循代码规范（development/spec.md）
- 代码审查覆盖率 100%
- 使用 ESLint / Prettier 进行代码检查
- 避免技术债，定期重构

## 10. 安全策略

### 10.1 安全现状

- 2 个严重漏洞

### 10.2 安全修复优先级

| 优先级 | 漏洞类型 | 修复计划 |
|--------|---------|---------|
| 立即修复 | 加密实现（Base64 → AES）、弱签名算法（MD5 → SHA-256） | v3.0.x |
| 尽快修复 | CSRF Token 随机数、敏感数据明文存储 | v3.0.x |
| 计划修复 | SQL 注入检测优化、XSS 防护完善、请求速率限制 | v3.1.0 |
| 可选修复 | 日志敏感信息、输入验证、安全响应头 | v3.2.0 |
